Here's where your architecture becomes interesting. 🌚

You could manage both using a process supervisor such as PM2.

Official documentation: [PM2 Documentation](https://pm2.keymetrics.io/docs/usage/quick-start/?utm_source=chatgpt.com)

Advantages

Simple to implement.

No extra infrastructure required.

Workers can continue after a WhatsApp request finishes.

Multiple jobs can be scheduled and managed.

The bot remains responsive while jobs execute.


The catch

A background process is not the same as a durable agent.

If the machine suspends, the worker crashes, or the sandbox is destroyed, your agent may stop.

Your architecture must handle those events rather than assuming a process will live forever.

Also, your sandbox advertises automatic suspension after 30 minutes of inactivity. Verify exactly what counts as activity and whether a running command prevents suspension. Don't assume that an agent running inside the sandbox will automatically keep the machine alive.

For your current setup, this is the approach I'd start with.

5. Build the agent executor around a persistent session

Your existing sandbox is already capable of running tasks, so you probably don't need to rebuild the execution engine.

Instead, wrap the current execution logic in a long-lived job executor.

For example:

async function executeAgent(job) {
  await updateJob(job.id, {
    status: "starting",
    started_at: new Date().toISOString()
  });

  try {
    const result = await runAgent({
      task: job.task,
      context: job.context,

      // Persist progress while executing.
      onProgress: async (progress) => {
        await updateJob(job.id, {
          status: "running",
          progress,
          updated_at: new Date().toISOString()
        });
      },

      // Persist resumable state when supported.
      onCheckpoint: async (checkpoint) => {
        await saveCheckpoint(job.id, checkpoint);
      }
    });

    await updateJob(job.id, {
      status: "completed",
      result,
      completed_at: new Date().toISOString()
    });
  } catch (error) {
    await updateJob(job.id, {
      status: "failed",
      error: String(error),
      completed_at: new Date().toISOString()
    });
  }
}

runAgent, updateJob, and saveCheckpoint are illustrative interfaces—you'd connect them to your existing agent runtime and storage implementation.

One critical design decision

Don't simply call the current agent function and assume it will survive for hours.

Inspect how your existing agent handles:

Tool execution timeouts.

Sandbox command lifetimes.

Agent iteration limits.

Context-window exhaustion.

Network failures.

Browser sessions.

Process restarts.


If it currently runs a single request-response loop with a short timeout, you'll need to make that execution loop resumable or split the task into smaller steps.

For example, the agent could execute a task in stages:

Stage 1: Inspect repository
         |
         v
Stage 2: Create implementation plan
         |
         v
Stage 3: Implement changes
         |
         v
Stage 4: Run tests
         |
         v
Stage 5: Review and report

After each stage, persist the state required to continue.

If the process crashes after Stage 3, the worker should recover the checkpoint and resume safely rather than starting from scratch.

However, only resume from a checkpoint if the agent runtime and its tools actually support it. Otherwise, persist the completed stages and reconstruct the next step from those results.

8. Make the agent survive restarts

This is the difference between a background task and a genuinely persistent agent system.

Imagine this:

1. You start a two-hour coding task.


2. The worker runs for 40 minutes.


3. The server restarts.


4. Jen404 starts again.



What happens?

A weak implementation loses the task.

A good implementation recovers it.

Recovery strategy

On startup:

1. Load unfinished jobs from the database.


2. Identify jobs that were running when the worker stopped.


3. Check whether their execution processes or remote sandbox sessions still exist.


4. Reattach to surviving executions when supported.


5. Otherwise, resume from a valid checkpoint or mark the job interrupted.


6. Requeue only jobs that can safely be retried.



Don't blindly rerun every running job. An agent might have already pushed code, sent a message, or performed another external action before the crash. Retrying without checking could duplicate that action.

I'd use a lease or heartbeat for each worker. A worker periodically updates its last-seen timestamp; the recovery process can detect stale workers and reconcile their jobs.

Also, give each job an execution deadline and a cancellation mechanism. Persistent should mean recoverable within defined limits, not unlimited execution.

9. The biggest architectural question: Where should the agent run?

Your current 404machine is powerful enough to start, but I'd separate the agent controller from the sandbox execution environment.

Here's why.

If the bot, worker, and execution environment all depend on the same sandbox staying alive, one suspension event can interrupt everything.

A stronger architecture looks like this:

Later, if you need stronger reliability, you can move the job controller and database to a more persistent host and make 404machine a dedicated execution worker.

10. How I'd handle the job queue

For the initial implementation, I'd avoid adding unnecessary infrastructure.

Phase 1: SQLite + a worker process

Use SQLite as the persistent job store and queue source.

The worker claims jobs transactionally so that two workers don't execute the same job simultaneously.

You should also:

Limit the number of concurrent agents.

Use a lease to recover jobs abandoned by dead workers.

Persist the current attempt number.

Apply exponential backoff to eligible retries.

Use a unique execution identifier to prevent duplicate starts.

Keep job history and logs available after completion.


SQLite is a reasonable choice for a single-machine prototype. Use a transactional claim operation rather than a simple SELECT followed by an UPDATE, which can race if multiple workers are active.

Phase 2: A dedicated queue

Once the workload grows, consider BullMQ.

Official documentation: [BullMQ Documentation](https://docs.bullmq.io/?utm_source=chatgpt.com)

BullMQ provides useful queue primitives, including delayed jobs, retries, concurrency control, and worker coordination.

Your architecture would then become:

WhatsApp Bot
     |
     v
BullMQ Queue
     |
     v
Agent Workers
     |
     v
404machine

You'd also need a persistent Redis deployment.

One subtle point: BullMQ can manage job execution and retries, but it doesn't automatically make an arbitrary AI agent resumable after a process crash. You still need your own checkpointing, sandbox recovery, and duplicate-action handling.

My recommendation: Start with SQLite if you want the simplest single-machine implementation. Introduce Redis and BullMQ when you need multiple workers, more advanced scheduling, or higher throughput.

Resource limits

Per-job runtime limits.

Memory and CPU monitoring.

If an agent launches Chromium, Gradle, or several Node.js processes, it may consume substantially more resources than a simple research task.

12. Add cancellation and human approval

Since the agents can execute commands, edit projects, and interact with a browser, I'd add controls before allowing them to run unattended for hours.

For example:

/cancel 73Ak82998839

The system should request cancellation, signal the execution process, and update the job state when execution has actually stopped.

Don't immediately label a job cancelled just because a cancellation request was received. It might take time for the process to terminate.

I'd also require explicit approval before sensitive external actions, such as:

Publishing a release.

Deleting important data.

Deploying to production.

Sending messages to third parties.

Spending money or initiating paid services.


An agent that needs approval should enter a waiting state and send a WhatsApp message explaining what it needs.

The user can then approve or reject the action, and the agent can continue if its runtime supports resumption.
